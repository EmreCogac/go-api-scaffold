# Go API Scaffold

Goal: turn a short project description into a working Go API skeleton with secure defaults. Don't ask unnecessary questions. Use the defaults below and only ask about whatever is missing from "Before you start" (one message, at most 4 questions).

## Before you start (ask only what is missing)

1. Client type: **mobile**, **web**, or **both**?
2. Is auth needed? (default: yes, email + password, JWT)
3. Project name and Go module path (e.g. `github.com/<user>/<project>`)
4. Any special requirements? (file uploads, websockets, queues, multi-tenancy, etc.)

If the user doesn't answer, proceed with defaults and state each assumption in one line at the end.

## Default technology choices

| Concern | Choice |
|---|---|
| Router | Gin |
| ORM | GORM (pgx driver) |
| Database | PostgreSQL 16 |
| Migrations | golang-migrate (SQL files in `migrations/`) |
| Config | `.env` + `config.yaml` via `viper`; env always overrides yaml |
| Validation | go-playground/validator |
| Logging | stdlib `log/slog` (JSON) |
| Auth | JWT (golang-jwt/v5) + bcrypt (cost 12) |
| Rate limiting | `ulule/limiter` or a simple in-memory token bucket |
| API docs | swaggo/swag |
| Tests | testing + testify; testcontainers or a separate test DB for DB tests |

If the user prefers something else (Fiber, sqlc, MySQL, ...), use it, but apply the security rules unchanged.

## Project structure

```
<project>/
├── cmd/api/main.go
├── internal/
│   ├── config/          # env + yaml loading, validation
│   ├── server/          # router, middleware registration
│   ├── middleware/      # auth, cors, ratelimit, secure headers, request id
│   ├── auth/            # handler, service, repository
│   ├── user/            # handler, service, repository, model
│   └── platform/        # db connection, logger, error types
├── migrations/          # 000001_init.up.sql / .down.sql
├── docs/                # swagger output (generated by `make swag`)
├── config.yaml
├── .env.example
├── .gitignore
├── .dockerignore
├── .golangci.yml
├── Dockerfile
├── docker-compose.yml
├── Makefile
└── README.md
```

Layers: handler (HTTP) -> service (business rules) -> repository (DB). Handlers never touch the DB directly.

## Files to generate and their rules

### .env.example (never generate a real .env, only the example)
```
APP_ENV=development
APP_PORT=8080
DATABASE_URL=postgres://app:app@localhost:5432/app?sslmode=disable
JWT_ACCESS_SECRET=change-me-min-32-chars
JWT_REFRESH_SECRET=change-me-min-32-chars
JWT_ACCESS_TTL=15m
JWT_REFRESH_TTL=720h
CORS_ALLOWED_ORIGINS=http://localhost:3000
RATE_LIMIT_RPS=10
```
- Do not invent real-looking secrets; leave placeholders. Tell the user to generate them with `openssl rand -base64 48`.
- In production, config validation must **refuse to start** if a secret is shorter than 32 characters or still a placeholder.
- Add `.env` to `.gitignore`.

### config.yaml
No secrets, only behavior settings: port, timeouts, log level, rate limit, CORS, DB pool (`max_open_conns: 25`, `max_idle_conns: 5`, `conn_max_lifetime: 30m`). Environment variables override yaml.

### docker-compose.yml
PostgreSQL service (with healthcheck and a named volume); the API service uses `depends_on: condition: service_healthy`. Read passwords from `.env`.
- Inside the compose network the API must reach the DB at host `db` (the service name), not `localhost`; override `DATABASE_URL` for the API service accordingly.
- Publish the DB port on loopback only (`127.0.0.1:5432:5432`), never on `0.0.0.0`.

### Dockerfile
Multi-stage build, final stage `gcr.io/distroless/static` or alpine, **non-root user**, `CGO_ENABLED=0`.

### Makefile
`run`, `build`, `test`, `lint`, `vuln`, `migrate-up`, `migrate-down`, `swag`, `docker-up`.

### main.go
Graceful shutdown (SIGINT/SIGTERM, 10 s). Set `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` and `IdleTimeout` on `http.Server`. Provide `/healthz` (liveness) and `/readyz` (DB ping) endpoints. Register panic recovery and request logging middleware (method, path, status, latency, `request_id`; no bodies or tokens).

### Initial migration (`000001_init`)
Use UUID primary keys (no sequential IDs to enumerate). Always write the `.down.sql` too.
- `users`: `id`, `email` (case-insensitive unique: `citext` or a unique index on `lower(email)`), `password_hash`, `role` (default `user`), `failed_login_attempts`, `locked_until`, `created_at`, `updated_at`.
- `refresh_tokens`: `id`, `user_id` (FK, `ON DELETE CASCADE`), `token_hash`, `family_id`, `device_id` (nullable), `expires_at`, `used_at`, `revoked_at`, `created_at`. Index on `token_hash` and `user_id`.
- `devices` (mobile or both only): see the Mobile section.

### Error response format
One shape for every error, never anything else:
```json
{ "error": { "code": "invalid_credentials", "message": "invalid email or password", "request_id": "..." } }
```
Map domain errors to status codes in one place (`internal/platform`), not in each handler.

## Behavior by client type

### Mobile
- Auth: short-lived access token (15 min) + **rotating refresh token**. Refresh tokens are opaque random values (32 bytes from `crypto/rand`, base64url), stored as a **SHA-256 hash** in the DB (not bcrypt; they are high-entropy and looked up by hash). Issue a new one on every use, invalidate the old one, and keep them in the same `family_id`. If an already-used token is presented again, revoke all of that user's refresh tokens (theft detection).
- Carry tokens in the `Authorization: Bearer` header. Do **not** set up cookies or CSRF.
- CORS is not needed; do not add CORS middleware.
- `devices` table: `user_id`, `device_id`, `platform`, `push_token`, `last_seen_at`.
- Read `X-App-Version` and `X-Platform` headers; if the version is below the configured `min_supported_version`, return `426 Upgrade Required`.
- Rate limit per user/device (IPs are often shared on mobile networks); unauthenticated endpoints (login, register) fall back to IP.
- Keep responses small: pagination (`limit`, `cursor`) is required on list endpoints.

### Web
- Auth: access token kept in memory (JS), refresh token in an **httpOnly + Secure + SameSite=Lax/Strict cookie**. Every state-changing endpoint that relies on cookies needs CSRF protection (double-submit token or `Origin`/`Referer` check).
- CORS: only origins in `CORS_ALLOWED_ORIGINS`; never use `*` when `AllowCredentials` is on.
- Security headers: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Content-Security-Policy: default-src 'none'` for the API.
- Rate limit per IP; if behind a proxy, configure `SetTrustedProxies`.

### Both
Separate the auth endpoints into `/api/v1/mobile/...` and `/api/v1/web/...` (different token transport), and keep the business logic (`service` layer) shared.

## Security checklist (apply to every project)

1. Passwords use bcrypt (cost >= 12); never log plaintext passwords. Enforce a length of 8 to 72 **bytes** (bcrypt silently ignores anything after byte 72). Normalize emails (trim + lowercase) before lookup and storage.
2. Validate all input with the validator; limit request body size (`http.MaxBytesReader`, default 1 MB).
3. Use only GORM's parameterized queries; never build SQL by string concatenation. If `Raw`/`Exec` is needed, use `?` placeholders.
4. **Object-level authorization**: on endpoints like `GET /orders/:id`, verify the record belongs to the requesting user (prevents IDOR).
5. Use DTOs for create/update; never bind request bodies directly to models (prevents mass assignment; fields like `role` or `is_admin` can't be set from outside).
6. Strict rate limits on login, register and password reset (e.g. 5 per minute) plus temporary per-account lockout.
7. Login errors say "invalid email or password"; never reveal whether an account exists. When the email is unknown, still run a bcrypt comparison against a dummy hash so response time doesn't leak it. The same applies to register and password reset responses.
8. Never return stack traces or SQL errors to clients; log them server-side and return a generic message plus a `request_id`.
9. Generate a `request_id` for every request and include it in logs. Never log tokens, passwords, full card numbers or national ID numbers.
10. JWT: pin the algorithm (HS256 or RS256, reject `none`), validate `exp`, `iat`, `sub`, and use different secrets for access and refresh tokens.
11. In production, DB connections use `sslmode=require` or stronger; the app's DB user must not be a superuser.
12. Run Gin in `release` mode (`gin.SetMode(gin.ReleaseMode)` when `APP_ENV=production`).
13. Dependency scanning: add `govulncheck ./...` to the Makefile as `make vuln`.
14. If file uploads exist: enforce size limits, validate content type, never trust the original filename, and store files outside the web root.
15. Role checks live in a reusable middleware (`RequireRole`); the role is read from the DB or a signed claim, never from request input. Default role is the least privileged one.
16. Swagger UI and any debug/pprof endpoints are disabled when `APP_ENV=production` (or protected behind auth).
17. Compare secrets and tokens with `crypto/subtle.ConstantTimeCompare`, not `==`.

## Reviewing an existing project (security review mode)

When the user wants an existing Go API reviewed:
1. Read the project (router, middleware, auth, repository layers).
2. Compare it against the checklist above, item by item.
3. Report findings as **Critical / High / Medium / Low**; for each give file:line, why it is risky, and a suggested fix. Use this shape per finding: `[Severity] file:line - title`, then *Risk*, then *Fix*. Close with the checklist items that passed, so the user sees what was verified.
4. Run `govulncheck ./...` if available and include its results.
5. Do not modify code until the user approves; present the report first, then propose fixes.

## Working rules

- If the target directory already contains files, list what would be overwritten and ask before touching anything.
- Pin a current stable Go version in `go.mod` and the Dockerfile (same version in both).
- Generate the skeleton first, then run `go mod tidy`, `go build ./...` and (if possible) `go vet ./...` to confirm it compiles. Never hand over code that doesn't build.
- Include a minimum of tests: password hashing, JWT validation (including the `none` algorithm and expired tokens), refresh-token rotation/reuse detection, and one IDOR check.
- One example resource (`user` + `auth`) and one migration are enough to start; don't guess at and bloat the project with the user's domain models.
- End with a short summary: the chosen stack, assumptions made, and first-run commands (`cp .env.example .env`, `make docker-up`, `make migrate-up`, `make run`).
- Never generate real secrets, passwords or API keys into files.
